# Detection Scenarios and Validation

These are the outcomes observed in this lab. They are useful portfolio evidence, but they do not establish that the environment is production-ready.

## Scenario 1 — File modification (FIM)
**Objective:** Detect a change to a monitored file.

**Test:** Modified `C:\\SOC-Lab\\test.txt`.

**Observed alert:**
- Rule ID: **550**
- Level: **7**
- Description: Integrity checksum changed
- Decoder: `syscheck_integrity_changed`
- Event: modified
- Detection mode: real-time

SHA-256 changed from:
- Before: `b5e29c8d4e6c8f3dfaf035bf16308623d8b95b9dd540df77d14e02989598bd5e`
- After: `9488476ae7a95964419cdd5a3dafc5eb089ebbeaeb045cbd6f54e483a0d9c328`

File size changed from 31 bytes to 52 bytes. This confirms that the configured FIM monitor detected the test modification.

## Scenario 2 — New file creation (FIM)
**Objective:** Detect a new file in the monitored directory.

**Test:** Created `C:\\SOC-Lab\\soc-test-2.txt`.

**Observed alert:**
- Rule ID: **554**
- Level: **5**
- Description: File added to the system
- Detection mode: real-time
- SHA-256: `07e780d2104c77b3d7d0c642e6da32dba2800fe3a0879559f13077204e36752a`

This confirms that new-file creation in the watched directory was detected.

## Scenario 3 — Failed Windows logons
**Objective:** Find failed interactive logon events.

**Search:** Windows Event ID **4625**, filtered to the monitored endpoint.

**Observed:** Two matching events within the selected 24-hour window. Wazuh rule **60122**, level **5**, described the event as a logon failure due to an unknown user or bad password.

One inspected event included logon type **2** (interactive), loopback source `127.0.0.1`, process `C:\\Windows\\System32\\svchost.exe`, authentication package `Negotiate`, and status `0xc000006d`.

**Assessment:** This confirms failed-logon telemetry was collected and searchable. It does **not** by itself prove malicious activity. The loopback source and process context require additional investigation before attributing the event to a user, service, or attack.

Suggested follow-up: compare timestamps and target account fields; review nearby successful and failed logons; correlate with process and service events; determine whether activity is expected; record a conclusion only after corroborating evidence is available.

## Scenario 4 — Sysmon telemetry
**Objective:** Confirm that Sysmon events reach Wazuh.

**Observed:** Events from `Microsoft-Windows-Sysmon/Operational` were available in the dashboard. A process-related alert for `sdbinst.exe` was generated by rule **92058**, level **12**, referring to an Application Compatibility Database launch and ATT&CK technique **T1546.011**.

**Assessment:** The event demonstrates telemetry and rule matching, not confirmed malicious behavior. Further triage should verify file path, signer, parent process, command line, hash, user, and surrounding events.

## Scenario 5 — Vulnerability detection
**Objective:** Review software vulnerability findings from endpoint inventory.

**Observed:** The dashboard showed VirtualBox-related CVE findings, including medium- and high-severity findings for the installed VirtualBox version.

**Assessment:** Vulnerability detection is operational. A finding means inventory/version data matched vulnerability intelligence; it does not prove exploitation. Validate the affected product/version, vendor advisory, exposure, and remediation guidance before prioritizing.

## Summary
The lab has demonstrated endpoint log collection, FIM detection for file modification and creation, searchable failed-logon events, Sysmon ingestion, and vulnerability findings. More controlled tests and correlated investigations are needed before making broader claims about detection coverage.
